# 인증 범위 — 데모 전제 Design Review

작성일 2026-08-05 · 상태 **확정(5단계) — 애플리케이션 인증 없음** · 선행 [server-action-contract.md](server-action-contract.md), [screen-behavior.md](screen-behavior.md)

설계 순서 중 **⑤ 인증·인가** 단계다. 앞선 문서들이 "구현 착수 전 필수"로 남겨 둔 항목을 이 문서로 닫는다.

## 결정

**애플리케이션 인증을 구현하지 않는다.** 이 프로젝트는 데모다.

- 로그인 화면, 세션, 사용자 테이블, `proxy.ts` 접근 제어를 만들지 않는다.
- Auth.js·`@auth/prisma-adapter`·Clerk 같은 의존성을 넣지 않는다.
- 모든 화면과 Server Action이 인증 없이 동작한다.

## 개발에 문제가 되는가 — 아니다

①~④ 설계 중 인증에 의존하는 항목이 없다.

- Server Action은 인증 없이 그대로 동작한다. ③의 시그니처·에러 코드·검증 스키마가 바뀌지 않는다.
- ④가 "권한이 목록 필터·버튼 노출을 바꾸니 화면 구현 전에 정하자"고 한 이유가 해소된다. **인증 없음은 "로그인하면 전원 관리" 단일 역할과 동일하고**, 그것이 시안이 그려진 관점이다. 시안대로 만들면 된다.
- 오히려 의존성과 DB 테이블이 줄어 구현량이 작아진다.

## 대신 반드시 지킬 것 2가지

### 1. Vercel Deployment Protection을 켠다

**Server Action은 공개 HTTP 엔드포인트다.** 화면에 버튼이 없어도 액션 ID를 아는 사람은 POST를 보낼 수 있다. Vercel 배포 URL은 공개이고 검색에 노출될 수 있다. 방치하면 데모 데이터가 삭제되거나 쓰레기 데이터가 들어온다.

- **Vercel Deployment Protection(Vercel Authentication)을 Preview와 Production 모두에 켠다.** 플랫폼 레벨 게이트라 애플리케이션 코드가 필요 없다.
- `robots.txt`와 `noindex`로 검색 노출을 막는다.
- 이 두 가지가 데모 목적의 보호 수단이다. 배포 체크리스트에 넣는다.

### 2. 실제 인사평가 **결과**를 넣지 않는다

제약을 이름이 아니라 **평가 결과의 실재성**에 건다(2026-08-06 결정).

- **인물은 자유롭게 추가한다.** 이름·부서·팀·직책에 제한을 두지 않는다.
- **평가 수치와 결과는 가상값을 쓴다.** 실제 인사평가 결과를 그대로 옮기지 않는다.

## 받아들이는 제약

- **감사 정보를 남길 수 없다.** 누가 등록·수정·삭제했는지 기록할 주체가 없다. `deletedAt`은 남지만 `deletedBy`는 없다. **없는 정보를 위한 컬럼을 미리 만들지 않는다.** `createdBy`·`updatedBy`·`deletedBy`를 스키마에 넣지 않는다.
- **레이트 리밋이 없다.** Deployment Protection이 사실상의 방어선이다.
- 사용자별 개인화(내 KPI 바로 보기 등)를 만들 수 없다.

## 나중에 인증을 붙일 때의 비용

구조를 뒤집지 않는다. ③에서 DB 접근을 `service.ts`로 모아 둔 것이 그대로 이점이 된다.

| 바꿀 곳 | 내용 |
|---|---|
| 목록·상세 조회 | `service.ts`의 공통 where 조각에 소유자 조건을 한 번 끼운다. 개별 쿼리는 손대지 않는다 |
| Server Actions | 각 액션 진입부에 세션 확인을 추가한다. `ActionError`에 `UNAUTHORIZED` 코드를 더한다 |
| 화면 | 역할에 따른 버튼·필터 노출 분기. ④의 화면 구조 자체는 유지된다 |
| 사원 식별 | 로그인 아이디를 `employeeLoginId`와 매칭한다. ①이 사원 정보를 KPI 레코드에 직접 저장하므로 별도 조인이 필요 없다 |
| 스키마 | 세션·사용자 테이블 추가. 감사 컬럼이 필요하면 그때 넣는다 |

2역할(담당자/본인) 전환이 가장 가능성 높은 확장 경로다. 그때 `middleware.ts`가 아니라 **`proxy.ts`**를 쓴다 — Next 16에서 이름이 바뀌었고 Node.js 런타임에서 실행되므로 Prisma edge 우회책이 필요 없다.

## 검증 기준

- 배포 후 Deployment Protection이 켜져 있는지 확인한다. 로그아웃 상태의 브라우저로 Production URL을 열어 게이트가 걸리는지 본다.
- 씨드·DB의 평가 수치가 실제 인사평가 결과가 아닌지 확인한다(이름 자체는 제한하지 않는다).
- `robots.txt`가 크롤링을 막고 있는지 확인한다.
- 스키마에 `createdBy`·`updatedBy`·`deletedBy`가 없는지 확인한다(없는 정보를 위한 컬럼 금지).

## Out of Scope

- 로그인 화면·세션 관리·비밀번호 처리
- 역할 기반 접근 제어
- 감사 로그
- 레이트 리밋

## 미해결 질문

없음. 실제 직원 데이터 투입 계획이 생기면 이 문서를 다시 열고 인증 방식부터 결정한다.
