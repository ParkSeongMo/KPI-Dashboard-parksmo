# KPI 도메인 모델·계산 규칙 Design Review

작성일 2026-08-05 · 상태 **확정(1단계)** · 근거 `docs/image/` 시안 4장 + 사용자 결정

설계 순서 중 **① 도메인 모델·계산 규칙** 단계다. ② 스택·프로젝트 구조, ③ API 계약, ④ 화면별 동작·검증은 별도 문서로 이어서 남긴다.

## 목표

- KPI 평가 1건의 데이터 구조와 달성률 계산식을 프론트엔드·백엔드가 같은 기준으로 구현할 수 있게 잠근다.
- 시안 4장(목록/등록/상세/수정)에서 역산 가능한 사실과, 사람이 결정해야 했던 항목을 분리해 기록한다.

## 사용자 시나리오

- 주 시나리오: 평가 담당자가 `KPI 등록`에서 사원 정보(아이디·이름·부서명·팀·직책)와 기준 기간(연도 + 반기)을 입력하고, KPI 항목을 여러 개 추가한다. 항목마다 평가영역·항목명·측정지표·목표치·목표개수·달성개수·가중치를 넣는다. 가중치 합이 100%가 되면 저장할 수 있다.
- 보조 시나리오: 담당자가 목록에서 부서명·팀·이름·직책·기준 기간으로 검색해 대상을 찾고, `상세보기`로 종합 달성률과 평가영역별 비중, 항목별 계산 결과를 확인한다. 값이 틀렸으면 `수정`에서 기존 값을 고치거나 항목 순서를 바꾸고 다시 저장한다.

## 도메인 모델

### KpiEvaluation — 평가 1건 (사원 1명 × 기준 기간 1개)

| 필드 | 타입 | 필수 | 근거 |
|---|---|---|---|
| `id` | 식별자 | — | 상세/수정 진입에 필요 |
| `employeeLoginId` | 문자열 | 필수 | 수정 시안 `아이디 *` = `lee.yh` |
| `employeeName` | 문자열 | 필수 | 등록/수정 `이름 *` |
| `departmentName` | 문자열 | 필수 | 등록/수정 `부서명 *` |
| `teamName` | 문자열 | **선택** | 목록에 팀이 `-`인 행이 2건 있다(강수연, 한명수). 등록 폼의 `팀`에도 `*`가 없다 |
| `position` | 문자열 | 필수 | 등록/수정 `직책 *`은 **셀렉트**다. 자유 입력이 아니라 고정 목록에서 고른다. 관찰값 8개와 상수 관리 방식은 [screen-behavior.md](screen-behavior.md)의 「시안 재정독에서 나온 수정 사항」 참조 |
| `baseYear` | 정수 | 필수 | 등록/수정 `기준연도 *`도 **셀렉트**다. 시안 값은 `2026`. 범위는 확인 필요 |
| `baseHalf` | `FIRST` \| `SECOND` | 필수 | **결정: 반기 단위**. 시안 라벨은 `기준분기`지만 값과 표기가 전부 `하반기`/`2026년 하반기`다. 라벨을 `기준 반기`로 고친다 |
| `items` | `KpiItem[]` | 최소 1개 | 등록 폼이 항목 1개로 시작하고 `+ 항목 추가`로 늘린다 |

**사원 정보는 KPI 레코드에 직접 저장한다.** 사원 마스터 테이블과 FK를 두지 않는다.
- 이유: 시안의 등록/수정 폼이 다섯 필드를 모두 자유 입력으로 받는다. 사원 CRUD·마이그레이션 없이 시안과 정확히 일치하고, 조직 개편 후에도 평가 당시 소속이 보존된다.
- 대가: 같은 사원을 여러 기간에 등록하면 부서명·직책 표기가 엇갈릴 수 있다. 목록 필터가 문자열 매칭이므로 표기 불일치가 검색 누락으로 이어진다. 완화책은 ④ 단계에서 자동완성으로 다룬다.

### KpiItem — KPI 항목

| 필드 | 타입 | 필수 | 근거 |
|---|---|---|---|
| `evaluationArea` | 문자열 | 필수 | 등록/수정 `평가영역 *`. 자유 입력 텍스트다(시안 값: 개발, 품질, 운영) |
| `itemName` | 문자열 | 필수 | `항목 *` |
| `metric` | 문자열 | 선택 | `측정지표`에 `*`가 없다 |
| `targetValue` | 문자열 | 선택 | `목표치`에 `*`가 없다. 값이 `분기 5건 이상`, `월 2건`, `주 3건`, `300ms 미만`, `서비스율 1개`처럼 서술형이라 **계산에 쓰지 않는 표시용 텍스트**다 |
| `targetCount` | 정수 ≥ 0 | 필수 | `목표개수 *`. **0을 허용한다** — 목표 미설정으로 보고 달성률을 100%로 계산한다(아래) |
| `achievedCount` | 정수 ≥ 0 | 필수 | `달성개수 *`. 등록 시안 기본값 `0` |
| `weight` | 백분율 | 필수 | `가중치 (%) *` |
| `sortOrder` | 정수 | 필수 | 수정 시안에 항목 순서 이동 `↑` `↓`가 있다. 표시 순서를 서버가 보존해야 한다 |

## 계산 규칙

상세 시안의 3개 행 숫자로 전부 역산·검증했다.

```text
항목 달성률(%)   = targetCount = 0 ? 100 : min(achievedCount / targetCount × 100, 100)
항목 가중점수     = 항목 달성률 × weight / 100
종합 달성률(%)   = Σ(항목 가중점수)
평가영역 비중(%) = Σ(해당 영역 항목의 weight)
```

`min(..., 100)` 상한은 ③에서 결정했다([server-action-contract.md](server-action-contract.md)). `achievedCount`가 `targetCount`를 넘는 입력은 허용하되 달성률만 100%로 자른다. 가중치 합이 100%로 강제되므로 **종합 달성률은 항상 0~100% 안에 있다.**

### 목표개수 0 = 목표 미설정 → 달성률 100% (2026-08-05 결정)

`targetCount`에 **0을 허용하고, 그 항목의 달성률을 100%로 계산한다.** 목표를 세우지 않은 항목이므로 달성한 것으로 본다. 0으로 나누기도 함께 사라진다.

- 이전 결정(`targetCount ≥ 1` 강제, 0이면 달성률 0)을 대체한다.
- 화면에는 **별도 표기를 붙이지 않는다.** 달성률만 `100.0%`로 나온다. `(상한)`도 붙지 않는다 — 초과 달성이 아니기 때문이다. 목표개수 열에 `0`이 그대로 보이므로 원인을 알 수 있다.
- `achievedCount`는 0을 허용한다(기존과 동일).
- **부작용**: 모든 항목의 목표개수를 0으로 두면 가중치 합 100%만 맞춰도 종합 달성률이 100%가 된다. 목표 미설정을 만점으로 보는 규칙의 필연적 결과이며, 이를 막는 검증은 두지 않았다.

검증 (상세 시안 `홍길동 / 2026년 하반기`):

| 평가영역 | 항목 | 목표/달성 | 가중치 | 달성률 | 가중점수 |
|---|---|---|---|---|---|
| 개발 | 신규 기능 배포 | 10 / 9 | 40% | 90.0% | 36.0 |
| 개발 | 기술 부채 정리 | 10 / 8 | 30% | 80.0% | 24.0 |
| 품질 | 코드 리뷰 참여 | 10 / 10 | 30% | 100.0% | 30.0 |

- 가중점수 합 36.0 + 24.0 + 30.0 = **90.0** → 상세 헤더 `90.0%`와 일치.
- 평가영역 비중 개발 40+30 = **70%**, 품질 **30%** → 도넛 차트 `개발 (70%)`, `품질 (30%)`와 일치.

### 반올림

- **내부 계산은 반올림하지 않는다.** 항목 달성률·가중점수를 중간에 반올림하면 종합 달성률에 누적 오차가 생긴다.
- **표시 시점에만 소수 1자리로 반올림한다**(HALF_UP). 시안의 표기가 전부 소수 1자리다(`77.6%`, `85.5%`, `26.7%`, `36.0`, `100.0%`).
- 백엔드는 반올림하지 않은 값을 함께 내려주고, 표시 반올림은 한 곳에서만 처리한다. 프론트와 백엔드가 각자 반올림해 1자리에서 갈리는 것을 막는다.

### 종합 달성률 배지

| 배지 | 구간 | 색 |
|---|---|---|
| `양호` | 80% 이상 | 초록 |
| `우려` | 60% 이상 80% 미만 | 주황 |
| `미달` | 60% 미만 | 빨강 |

시안 10건과 전부 맞는다: 92.0·90.0·85.5·85.0 → 양호, 77.6·73.0·60.0 → 우려, 26.7·25.0 → 미달. 경계는 이상/미만으로 고정하고 상수로 둔다.

## 입력 / 출력

- 입력: 등록/수정 폼의 사원 정보 8필드 + KPI 항목 배열. 목록 화면의 검색 조건(부서명·팀·이름 텍스트, 직책·기준 기간 셀렉트).
- 출력: 저장된 `KpiEvaluation`. 목록에는 사원 정보 + 종합 달성률 + 배지, 상세에는 종합 달성률·평가영역 비중·항목별 달성률/가중점수.
- 종합 달성률과 항목 달성률은 **저장하지 않고 조회 시 파생 계산**한다. 시안 규모가 `총 12건`이라 집계 비용이 문제되지 않고, 저장하면 항목 수정 시 갱신 누락으로 값이 어긋날 위험이 생긴다. 목록 정렬·필터가 달성률 기준으로 확장되면 재검토한다.

## 제약

- 기술 제약: 스택 미정(② 단계에서 결정). 계산식은 프론트엔드 실시간 표시와 백엔드 저장·조회 양쪽에 들어가므로 **한쪽을 SSOT로 정하고 다른 쪽이 따라간다**. 백엔드 계산을 SSOT로 두고, 프론트엔드는 입력 중 미리보기 용도로만 같은 식을 쓴다.
- 비즈니스 제약: 가중치 합 100% 강제(아래). 시안 밖의 승인·결재 흐름은 확인된 바 없다.

### 가중치 합 100% — 저장 차단

- **합이 정확히 100%가 아니면 저장하지 않는다.** 등록·수정 모두 동일하다.
- 프론트엔드는 하단 고정 바에 현재 합계를 상시 표시한다. **저장 버튼은 비활성하지 않고**, 누르면 검증 실패를 알리고 첫 오류 필드로 포커스를 옮긴다(접근성 이유 — ④에서 결정). 백엔드도 같은 검증을 하고 위반 시 거부한다(프론트 검증만 믿지 않는다).
- **시안 문구를 고쳐야 한다.** 현재 시안은 `가중치 합이 100%가 아닙니다 (현재 80%). 미달분은 달성률에 반영되지 않습니다`인데, 저장을 차단하면 뒷문장은 도달할 수 없는 안내다. `저장하려면 가중치 합이 100%여야 합니다 (현재 80%)`처럼 바꾼다. 수정 시안의 합계 80% 상태도 저장 불가 상태로 다시 읽는다.
- 합이 100%로 강제되므로 종합 달성률은 모든 항목이 100% 달성일 때 정확히 100.0%가 된다.

## 엣지케이스

- `targetCount = 0` → 목표 미설정으로 보고 달성률 100%. 0으로 나누기가 발생하지 않는다. `achievedCount`가 0보다 커도(예: 0/5) 100%다.
- 항목 0개 → 가중치 합이 0%이므로 100% 규칙에 자동으로 걸려 저장 불가. 최소 1개 메시지를 따로 보여준다.
- `achievedCount > targetCount` → 달성률이 100%를 넘는다. **미해결**(아래).
- 평가영역이 자유 입력이라 `개발`/`개발 `/`개발팀`처럼 갈라지면 상세 도넛 그룹이 쪼개진다. 저장 시 앞뒤 공백을 제거하고, ④ 단계에서 기존 값 자동완성을 다룬다.
- 팀이 빈 값이면 목록에 `-`로 표시한다(시안과 동일).
- 항목 순서 이동 중 `sortOrder`가 중복되거나 비면 표시 순서가 흔들린다. 저장 시 서버가 0부터 다시 부여한다.
- 가중치를 정수로만 받으면 3개 항목 균등 배분에서 100%를 맞출 수 없다(33+33+33=99). **미해결**(아래).
- 목록 필터를 모두 비우고 검색 → 전체 조회로 동작한다. 초기화 버튼은 필터만 비우고 재조회한다.

## 검증 기준

- 기능 검증
  - 상세 시안 데이터(10/9·40%, 10/8·30%, 10/10·30%)를 넣으면 항목 달성률 `90.0/80.0/100.0`, 가중점수 `36.0/24.0/30.0`, 종합 달성률 `90.0%`, 배지 `양호`, 영역 비중 `개발 70% / 품질 30%`가 나온다.
  - 목록 시안 10건의 달성률을 넣으면 배지가 **양호 5건·우려 3건·미달 2건**으로 나온다(양호: 92.0·90.0·85.5·85.0·85.0 / 우려: 77.6·73.0·60.0 / 미달: 26.7·25.0). 경계 80.0은 양호, 79.9는 우려.
  - 가중치 합 99% 또는 101%로 저장을 시도하면 프론트에서 저장 버튼이 비활성이고, 백엔드 직접 호출도 거부된다.
  - `targetCount = 0`을 저장할 수 있고, 그 항목의 달성률이 `100.0%`로 나온다. 상세 표에 `(상한)`이나 다른 표기가 붙지 않는다.
- 비기능 검증
  - 계산 함수는 프론트/백엔드 어디에 있든 순수 함수로 분리해 단위 테스트한다. 위 두 데이터셋을 고정 픽스처로 쓴다.
  - 반올림은 표시 계층 한 곳에서만 수행되고, 계산 계층에는 반올림이 없다는 것을 테스트로 고정한다.

## Out of Scope

- 스택·프로젝트 구조·빌드 명령 (② 단계)
- API 엔드포인트·요청/응답 스키마·에러 코드 (③ 단계)
- 화면별 상호작용·유효성 메시지·접근성 (④ 단계)
- 사원 마스터, 조직도, 인증/인가, 결재·승인 흐름
- 엑셀 내려받기, 알림, 감사 로그 — 시안에 없다
